# Justification

**Commands.** I listed exact `.venv/bin/` invocations for install, test and lint because the project's environment lives in `.venv/`, and a bare `pytest` or `ruff` may not resolve. I made `pytest -v` mandatory before finishing any task, and in all three sessions the run happened and caught nothing, so the rule worked but was never tested by a failure. Its value showed up as the test count growing from 5 to 13 with every run green. If I had to cut the file in half, I would drop the single-file pytest line, since Claude can derive it from the full command.

**Architecture.** I wrote the layering as `routes/` -> `services/` -> `repositories/` with a named canonical example for each layer, because a rule without a file to imitate is easy to paraphrase wrongly. Session 2 shaped it most: the "only import the layer directly below" sentence was the only thing steering `create_task` toward `user_repo` instead of `services/users.py`, so I added an explicit no-service-to-service-imports bullet, and a `find_by_user_id` bullet before Session 3. Session 3 followed both on the first try. If cutting, I would drop the description of what repositories return and keep the two import and data-access rules.

**Conventions.** I pointed at `services/users.py` as the pattern instead of describing it, because `services/tasks.py` started with no hints, docstrings or errors and Claude tends to copy the file it is editing. In Session 1 this worked: `get_task` came out with `NotFoundError`, `ValidationError`, hints and a docstring. The one observed weakness is that matching `get_user` produced the same user-id validation in three functions, which no rule addresses. If cutting, I would remove the test-placement bullet and keep the error-class and type-hint rules.

**Do not touch.** I phrased each rule as a prohibition on a named file or path (`services/users.py`, `utils/errors.py`, `tests/`, `pyproject.toml`) so a violation is checkable. Session 1 exposed that "never change a signature" contradicted the type-hint rule, so I defined "signature" as name, parameter names, order and defaults. None of the file-protection rules were exercised in any session. If cutting, I would drop the `.venv/`, `requirements.txt` and `pyproject.toml` bullet first, since it is the least likely to be violated.

**Team of three.** First, I would add a short Workflow section (branch naming, run `ruff check .` and `pytest -v` before every PR) and commit CLAUDE.md so all three developers' sessions behave identically, instead of depending on each person's habits. Second, I would move personal preferences into a gitignored `CLAUDE.local.md` and put path-specific rules into nested `services/CLAUDE.md` and `tests/CLAUDE.md`. Otherwise the shared root file collects conflicting tweaks, as my own file nearly did when the signature and type-hint rules clashed. Caveat: my sessions were not cold starts and produced no clear failures, so these conclusions rest on weaker evidence than a multi-person project would.
